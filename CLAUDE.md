## Overview
Starcade OS is a portable, controller-friendly in-game arcade for Starfield: an Aid item ("Starcade Pad", reusable) or an F9 hotkey opens a web-based launcher (hosted inside the third-party **OSF UI** framework's webview) offering 25 original HTML5/Canvas games plus a ported **Freedoom: Phase 1** (open-source Doom) — 26 total. Casino games wager real in-game credits. High scores/saves/achievements persist outside the Starfield save entirely, in `Documents/My Games/Starfield/Starcade/state.json`. Three layers, cleanly separated by language/runtime:

1. **Native SFSE plugin** (`Starcade.dll`, GPL-3.0-or-later) — `Native/src/main.cpp`, a single 428-line file (there's no `Native/include/` despite the build script referencing one — genuinely monolithic, not a gap in what got copied). On `kPostLoad` it registers with OSF UI (`Connect()`): a view (`starcade.arcade/launcher`), a settings schema (declares the `openKey` hotkey, default F9), 6 commands, and a hotkey subscription that opens the launcher directly. On `kPostDataLoad` it binds two Papyrus native methods (`BindPapyrus()`). It owns:
   - **State persistence** — `LoadState`/`SaveState` read/write `state.json` atomically (write to a `.tmp` file then rename), quarantine unparsable JSON to a `.bad` sibling instead of overwriting it, and repair legacy null per-game entries left over from older saves.
   - **Casino transaction state machine** (`DispatchCreditTransaction`) — validates action ∈ {balance, wager, payout, cancel}, amount bounds (0–1,000,000), rejects duplicate in-flight `requestId`s, enforces exactly one active wager at a time, enforces a hardcoded per-game payout-cap table (blackjack ×3, video-poker ×251, five-card-draw ×3, roulette ×36, slots ×101, casino-dice ×6, high-low ×8, red-mile-bets ×11, default ×3), and auto-refunds on a failed payout/cancel or a wager-cancel race. It never touches the player's inventory directly — that's Papyrus's job; native only validates and tracks pending-request/wager state.
   - **XP rules** (`OnCommand`'s `run.finish` handler) — first completed run +5, new personal best +10, rank-based bonus (rank 1 = +50, ≤3 = +25, ≤5 = +15, ≤10 = +10, plus +20 for repeat-rank-1-with-a-new-record), capped 10-entry recent-scores history per game. `IsXPGame` excludes the 9 casino ids and anything catalogued `category:"casino"`.
2. **Papyrus** (6 scripts, `Web-and-Papyrus/Source/`, all `x2357Starcade*`) — thin glue, not simulation:
   - `x2357StarcadePlayerAlias.psc` (`ReferenceAlias`) + `x2357StarcadeLaunchEffect.psc` (`ActiveMagicEffect`) — the actual pad-delivery mechanism. The alias grants the pad on `OnInit()`/`OnPlayerLoadGame()` if the player doesn't already have it; the effect (fired by using the pad) opens `OSFUI.OpenMenu("starcade.arcade/launcher")` and immediately re-grants the pad — that re-grant is what makes an Aid item Starfield would otherwise consume "reusable."
   - `x2357StarcadeTerminal.psc` (`ObjectReference`) — for a placed terminal/activator variant (its own comment explicitly warns not to attach it to quest terminals); blocks normal activation and opens the same launcher menu on player activation. A second, in-world entry point alongside the portable pad — not confirmed wired to any actual placed object in the available source (see Known issues).
   - `x2357StarcadeCredits.psc` — the only script that touches player state directly: resolves vanilla Credits (`Starfield.esm` form `0x0000000F`) by hardcoded FormID specifically to stay "property-free and compatible with existing 1.2.0 saves" (its own comment), adjusts the player's balance, and reports the result back to native.
   - `x2357StarcadeRewards.psc` — calls vanilla `Game.RewardPlayerXP` then reports back to native.
   - `x2357StarcadeNative.psc` (`Native Hidden`) — pure declaration shim (`ReportCreditResult`/`ReportXPResult`) implemented by `Starcade.dll`.
3. **Web launcher + 26 games** (`Web-and-Papyrus/starcade.arcade/launcher/`, MIT) — plain HTML/Canvas/JS, no build step, no minification (shipped fully editable in both the source archive and the live install — see Project layout). Each game runs in an `<iframe>`; `games/host.js` (`window.StarcadeHost`) is the per-game SDK, turning `score`/`finish`/`save`/`achievement`/`exit`/`wager`/`payout`/`cancel` calls into `postMessage({channel:"starcade",...})` up to the launcher shell (`launcher/main.js`). The launcher relays native-bound commands through `osfui.send(...)` — a bridge object it does **not** define itself: `launcher/index.html` loads `../../shared/osfui.js` before `main.js`, which at the real deployed path resolves to `SFSE/Plugins/OSFUI/views/shared/osfui.js` — supplied by **OSF UI itself**, not part of Starcade's own source. Full round trip for a casino wager, confirmed end to end: `game.js → StarcadeHost.wager() → main.js → osfui.send("starcade.arcade.credits.transaction",...) → native OnCommand → DispatchCreditTransaction → Papyrus x2357StarcadeCredits.ProcessTransaction → vanilla Credits adjusted → x2357StarcadeNative.ReportCreditResult → native → g_ui.SendToWeb(...) → osfui.on("starcade.credits",...) in main.js → postMessage into the game's iframe → game.js resolves its pending promise` (the promise wrapper is `games/casino-bank.js`, an 8-second-timeout convenience layer over `StarcadeHost`). Controller input rides a parallel path: OSF UI pushes raw gamepad state (`osfui.on("ui.gamepad",...)`), `main.js` remaps it to keyboard-equivalent keys (special-cased for `freedoom`/`starfall-blocks`/`minefield-protocol`) and re-injects via the same `{type:"input"}` postMessage `host.js` already listens for. `manifest.json` declares `permissions:{nativeBridge:true, filesystem:false, network:false}` — nothing in the web layer touches disk or network directly; the in-game "rival leaderboard" is a fully local deterministic simulation (`companionScores()` in `main.js`, hashed by game id against 10 named Starfield companions), not real player data. `catalog.js` also drives an in-UI license/provenance panel — every game object carries an `origin`/`source` string shown to the player.
   - **Freedoom is the one exception** to the host.js pattern: `games/freedoom/` ships a single ~40MB, ~90,000-line precompiled `voidfall-asm.js` (DoomGeneric via ading2210's DoomPDF fork, retargeted from a PDF-JS framebuffer to an HTML Canvas, built with Emscripten fastcomp 1.39.20 and `WASM=0`, music disabled) that implements the `postMessage` wire protocol itself instead of loading `host.js`. Engine build tooling (`Makefile.pdfjs`, `embed_file.py`/`generate.py`) lives in `Freedoom-Engine/` at the Complete Source root; `Freedoom-Engine/doomgeneric/build/*.o` are stale native-build leftovers, unrelated to the asm.js pipeline actually shipped.

## Conventions
- Papyrus scripts: `x2357Starcade<Role>.psc` naming (`Credits`, `Rewards`, `Native`, `LaunchEffect`, `PlayerAlias`, `Terminal`).
- Native command strings: dot-namespaced `starcade.arcade.<noun>.<verb>` (e.g. `starcade.arcade.credits.transaction`, `starcade.arcade.run.finish`).
- Game catalog ids: kebab-case, one per game folder under `launcher/games/` (e.g. `xeno-serpent`, `five-card-draw`) — id and display title can diverge (see Known issues).
- License boundary is per-component, not per-file-type: original web/Papyrus/launcher code is MIT; the native plugin is GPL-3.0-or-later (inherited from CommonLibSF/OSF UI SDK); Freedoom's engine is GPL-2.0 and its game data is BSD-3-Clause; the `Reference-Projects/upstream-html-games` reference collection is MIT under its own separate notice. Keep new code's license tag consistent with whichever of these four buckets it lands in.
