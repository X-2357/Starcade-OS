# How to give Michael Creation Kit work — the task-list format (handoff for any mod session)

Michael, 2026-09-14, after three tries at a "CK guide": *"i like the tasks like this."* This is the
format that worked and the ones that did not. Any Starfield mod session here (SSaW, AISS, Crew
Titles, Outpost Communities, Shore Leave, Settled Systems Exchange, the next one) should hand CK
work over exactly this way.

## The one rule

**A CK deliverable is a numbered checklist of single actions, not a document.** He goes into the
CK once, works top to bottom, saves, tells you. Anything that is not an action he performs in the
CK does not belong in the file.

## The format

```
# <Mod> CK tasks - <N> steps, in order, one action each

<one line: where any paste text lives>
Nothing here is already done. If a record is missing or named differently than written, stop and tell me.

## <FEATURE GROUP>

1. Open quest SSAW_NarionSkirmishTest -> script SSAW_NarionSkirmishQuestScript -> property ShipCrewValue -> pick ActorValue SpaceshipCrew.
2. Create MESG SSAW_MESG_DistressChoice, buttons in this order:  0 Search it yourself | 1 Pay a patrol to search | 2 Broadcast the position | 3 Let it go
3. Open TMLM SSAW_TMLM_Operations -> drag into this ITID order:  6, 1, 7, 8, 4, 2, 14, 10, 9, 3
4. Open quest X -> array UCRoster (6 entries, slot 0 to 5) -> set to:  0 LvlMarine_Recruit | 1 LvlMarine_Assault | ...

## THEN

N. Save the plugin. Tell me. I copy it to Package, MO2 and the repo and read every record above back out of it.
```

Rules, each one earned:

1. **One action per line.** "Open X -> property Y -> value Z." If a step needs two records, it is
   two steps. Never "see Block H".
2. **Numbered continuously across the whole file**, grouped under short `##` headings by feature.
   He works by number; a cross-reference is "task 64", never "the Long Game section".
3. **Exact EDIDs, exact values, exact button text.** Verify every EDID against the packaged plugin
   *before* writing the list (read it, do not remember it). "Pick a cargo hull" is not a step; name
   the record. When he says a step "wasn't specific", that is what he means — and it is the step he
   skips.
4. **Messages = an index list**: `0 A | 1 B | 2 C`. State when an index is a trap ("Cancel goes at 4,
   index 3 repeals"). **Warn against adding a "Back" button**: a script that maps out-of-range
   choices to a default turns "Back" into a real action (SSaW's distress menu: Back = Broadcast
   the position).
5. **Menu order = an ITID sequence** to drag into, back-link excluded. Renames are their own steps.
   **Adding pages is not enough — the index links are a separate step** and it is the one that
   gets forgotten (SSaW: 14 pages created, none linked).
6. **Arrays = slot-by-slot**: `0 A | 1 B | 2 C`. Say what an empty slot falls back to. Say if the
   script only reads slots 0–5 so extra entries do nothing.
7a. ⚠ **THRESHOLD, added 2026-09-25: rule 7 is for LONG or MULTI-LINE body text ONLY.** A short
    single-line value — a token, a name, a label, anything that fits on one line — goes **INLINE in
    the step itself**, indented as a code block. Sending him to a second file to fetch nineteen
    characters makes him alt-tab, hunt a Desktop file and lose his place, which is the exact
    friction rule 7 exists to remove. Michael, 2026-09-25, on a `<Alias=PlayerAlias>` probe:
    *"why the fuck did you put the text in a different file making me jump around and waste fucking
    time trying to find shit"*. Rule 7 was written for 27 pages of terminal body text; applying it
    to one line is following the letter against the purpose. **Rough line: one line and short
    enough to read in the step → inline. Multi-line, or long enough that a transcription slip is
    plausible → `.txt` file.**
7. **Paste text goes in separate plain `.txt` files, one per record, BODY ONLY** — no headers, no
   fences, no labels. Folder on the Desktop, filenames `NN_<EDID>.txt`, a `00_TITLES.txt` beside
   them. The task says "Body Text = the whole of NN_<EDID>.txt". A markdown file with 27 fenced
   blocks was "not set up for me to just copy and paste". **Tell him to select-all in the body
   field before pasting** — the 2026-09-14 round left the old page's last line on the end of 24
   of 27 pages because the paste did not replace the whole field.
8. **Optional is said inline** ("Optional: ...") and never mixed into a required step.
9. **Nothing done, nothing historical, nothing explanatory.** The repo docs keep the history and
   the why. He asked, verbatim, *"why the fuck does the ck guide have so many things that are
   already done?"* after receiving the full build guide, and *"it's hard to read that guide it's
   really messy"* after receiving a version with prose. The third version — bare numbered steps
   — was the one he liked.
10. **End with "Save. Tell me."** ⚠ **CORRECTED 2026-09-25 — this line used to be INVERTED and it
    cost real time.** It said the CK writes the `.esm` and the session syncs to a `.esp`. The truth
    is the other way round and it is Michael's standing workflow:

    > **`<mod>.esp` is the file you EDIT in the Creation Kit. `<mod>.esm` is GENERATED from it for
    > use in the game.** The `.esp` is the CK's active file and is left DISABLED in the load order;
    > the `.esm` is the one with the ESM header flag set and the one enabled in `plugins.txt`, and
    > it is what MO2 serves to the game.

    So seeing `[<mod>.esp]` in the CK title bar is **correct and expected** — it is not a mistake,
    not a wrong-file trap, and must never be reported as one. Michael, 2026-09-25, having to say it
    out loud: *"you know that .esp files are what you edit in the ck and .esm are generated for use
    in game"* and *"i should not have to tell you this and you are wasting usage"*.

    The session's job is unchanged and happens AFTER the `.esm` is generated: sync it to the MO2
    mod folder, `Release/Data` and the repo, then verify **by reading the edited records back out
    of the generated `.esm`** — never by comparing timestamps, and never by diffing the file (a CK
    save re-serialises the whole plugin; entry 130 measured 66,631 differing bytes from a one-field
    change). Reading the records back out of the `.esm` is also the one check that catches an edit
    failing to survive the `.esp` → `.esm` generation step.

## After he saves: the read-back and the round-2 list

Never mark a step done from his word or from a timestamp. Parse the saved plugin and check every
step against it, then hand back **a round-2 list in the same format containing only what is
left or went in wrong**, with the exact fix for each (for a paste that kept leftover text: the
literal string to delete). Retire the old list from the Desktop so there is one.

What the read-back checks, per step type:

| Step type | Check |
|---|---|
| property fill | VMAD property value resolves to the named record (resolve vanilla FormIDs from Starfield.esm, do not guess) |
| MESG | `ITXT` buttons, count and order exactly; flag extra buttons |
| TMLM order | item `ITID` sequence; renames by `ITXT`; `TNAM` links resolve (TNAM is **4 bytes** = submenu FormID in these plugins) |
| TMLM text | `FULL` and `BTXT` compared to the paste file after CRLF/whitespace normalisation; if the body *starts with* the expected text, report the tail as leftover |
| new records | exist, EDID spelled right (watch for pasted `EDID` prefixes), nothing links to strays |
| arrays | each slot resolved to an EDID; flag scripted vanilla variants (`_Boss` carries `ForceLegendaryActorScript`; use `_NoScript`) |

Tooling that exists: `SSaW\Tools\starfield_esm_reader.py` (records + simple VMAD), and the
2026-09-14 scratch `esm_review.py` pattern (struct-array VMAD, TMLM/MESG subrecords, plugin diff,
vanilla resolver). Copy the pattern; self-check the parser against a record whose value you
already know before believing any finding (rule 8 of the working rules).

## What he will and will not do

- He will do **any** amount of CK work if it is specific. Do not design around avoiding it.
- He will not read prose to find the action in it.
- He will skip a step that says "pick one" and do the ones that say "pick X".
- He notices when a feature's cost in CK records exceeds what a player can perceive; do not put
  such a feature on the list without saying what the player gets (working rule 12).
